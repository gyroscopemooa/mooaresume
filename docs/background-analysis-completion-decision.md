# MOOA Resume — 분석 완료를 서버가 책임지는 구조

> 결정일: 2026-08-22
> 상태: 최신 제품 결정
> 관련 문서: `docs/create-mode-and-pricing-decision.md`, `docs/polar-dynamic-quick-checkout-implementation.md`, `docs/build-mode-fill-in-decision.md`
> 우선순위: 동일 항목이 충돌하면 이 문서의 결정이 우선한다. 기존 문서는 수정하지 않는다.

## 1. 문제 — 브라우저를 닫으면 분석이 멈춘다

`/api/analysis-runs/quick/execute`를 호출하는 곳은 `quick-checkout-return.tsx` 한 파일뿐이고, 프로젝트에 예약 워커나 크론이 없다.

```
결제 완료
  → 브라우저가 execute 호출 → OpenAI 백그라운드 작업 시작(응답 ID 저장)
  → 브라우저가 반복 호출 → 완료 확인 → 검증 → 저장 → 이메일
```

가운데 화살표가 전부 **브라우저에서 나온다.** 그래서 창을 닫으면:

- OpenAI 쪽 작업은 끝나지만 **아무도 결과를 가져오지 않는다.** 실행은 `RUNNING`에 남는다.
- 완료 이메일은 저장 요청 안에서 발송되므로 **가지 않는다.**
- 10분 초과 자동 환불은 결제 상태 조회 라우트에서 트리거되는데, 그것도 열린 페이지만 호출한다. **환불도 안 된다.**

분석이 5~10분 걸리는 상품에서 "창을 닫지 마세요"는 받아들이기 어려운 제약이다. 그리고 결제는 이미 이뤄진 뒤이므로, 사용자가 창을 닫았다는 이유로 돈만 나가는 상태가 남는다.

## 2. 결정 — 서버가 실행을 끝까지 끌고 간다

예약 작업이 주기적으로 진행 중인 분석을 확인하고 완료·실패·환불까지 처리한다. 브라우저 폴링은 **결과를 빨리 보여주기 위한 수단**으로 남기고, 완료의 책임은 서버가 진다.

```
예약 작업(1~2분 주기)
  → RUNNING이고 응답 ID가 있는 실행을 조회
  → OpenAI 결과 확인
      완료  → 검증 → 저장 → 이메일
      실패  → 실패 기록(재시도 가능)
      대기  → 다음 주기로
  → 시작 후 10분 초과 → 자동 환불
```

## 3. 실행 경로는 하나만 둔다

새 로직을 만들지 않는다. 예약 작업은 브라우저가 부르던 것과 **같은 함수**(`advanceQuickBackgroundAnalysis`, 검증기, `createQuickAnalysisResult`, 저장소)를 부른다. 경로가 둘로 갈라지면 한쪽에만 고쳐진 규칙이 생기고, 그때부터 "브라우저로 열었을 때만 통과하는 결과"가 생긴다.

## 4. 중복 처리 방지 — 이미 데이터베이스가 막고 있다

예약 작업과 열린 브라우저가 같은 실행을 동시에 처리할 수 있다. 다음 장치가 이미 있으므로 새로 만들지 않는다.

| 장치 | 효과 |
|---|---|
| `complete_quick_analysis`가 `status = 'RUNNING'`을 `for update`로 확인 | 두 번째 완료 시도는 `ANALYSIS_RUN_NOT_COMPLETABLE`로 거부된다 |
| `analysis_results` 삽입의 `on conflict do nothing` | 결과가 두 번 저장되지 않는다 |
| `claim_quick_analysis_timeout_refund` | 환불 청구를 한 번만 통과시킨다 |

따라서 **중복 이메일**만 남는 위험이다. 이메일은 완료 처리가 성공한 경로에서만 보내므로, 완료가 한 번만 성공하면 이메일도 한 번만 나간다.

## 5. 접근 제어

예약 작업은 사용자 세션이 없다. 저장소는 이미 `SUPABASE_SECRET_KEY`(서비스 롤)로 동작하므로 추가 권한 작업이 필요 없다.

호출 자체는 공유 비밀로 막는다.

```
POST /api/analysis-runs/advance
Authorization: Bearer <ANALYSIS_CRON_SECRET>
```

- 비밀이 설정되지 않았으면 라우트는 **항상 거부**한다. 설정 누락이 곧 공개 엔드포인트가 되어서는 안 된다.
- 한 번 호출에서 처리할 실행 수에 상한을 둔다. 한 번에 전부 처리하려다 시간 제한에 걸리면 아무것도 끝나지 않는다.
- 요청 출처 검사는 하지 않는다. 예약 작업은 브라우저가 아니다.

## 6. 예약 방법 — 세 가지 중 선택

Cloudflare 크론 트리거는 워커의 `scheduled()` 핸들러를 호출하는데, OpenNext가 생성하는 워커에는 그 핸들러가 없다. 워커 생성 과정에 손대는 것은 배포 전체를 흔드는 일이라 채택하지 않는다.

대신 **HTTP로 라우트를 호출하는 스케줄러**를 둔다. 라우트가 본체이고 스케줄러는 교체 가능하다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **Supabase `pg_cron` + `pg_net`** | 이미 쓰는 인프라, 추가 서비스 없음 | 마이그레이션 필요, 비밀을 DB에 둬야 함 |
| GitHub Actions `schedule` | 설정이 쉽고 로그가 보인다 | 최소 주기가 5분, 지연이 잦다 |
| 외부 크론 서비스 | 즉시 사용 | 서비스가 하나 늘어난다 |

초기에는 어느 쪽이든 된다. 주기는 **1~2분**을 기준으로 한다. OpenAI 작업이 5~10분 걸리므로 그보다 짧으면 충분하고, 환불 판정(10분)보다는 훨씬 짧아야 한다.

## 7. 이 결정이 바꾸는 문구

결제 확인 화면의 안내를 되돌린다.

```text
지금:  이 창을 열어둔 채로 기다려 주세요. 완료되면 결과 화면으로 바로 이동합니다.
이후:  창을 닫아도 분석은 계속됩니다. 완료되면 이메일로 결과 링크를 보내드립니다.
```

**예약 작업이 실제로 도는 것을 확인한 뒤에만** 문구를 바꾼다. 순서를 뒤집으면 지키지 못할 약속을 다시 하게 된다. 한 번 이미 그렇게 했다.

## 8. 이메일이 실제로 나가려면

현재 발송은 두 가지가 모두 있어야 동작한다.

```
ANALYSIS_EMAIL_FROM   환경변수        없으면 SKIPPED_NOT_CONFIGURED
EMAIL                 Cloudflare 바인딩  없으면 SKIPPED_BINDING_MISSING
```

`.env.example`에 `ANALYSIS_EMAIL_FROM`이 없고, 로컬 개발 서버에는 Cloudflare 바인딩이 없다. **지금까지 완료 이메일이 발송된 적이 없다.** 예약 작업을 붙여도 이 두 가지가 없으면 이메일은 여전히 나가지 않는다.

수신 주소는 Supabase 인증 이메일(구글 로그인 계정)이며 Polar 결제 시 입력한 주소가 아니다. 두 주소가 다를 수 있다는 점은 별도 판단이 필요하다.

## 9. 하지 않는 것

- 재시도를 자동화하지 않는다. 검증 실패는 사용자가 확인하고 다시 시도하는 편이 낫다. 자동 재시도는 같은 이유로 세 번 실패해 시도 횟수만 소모할 수 있다.
- 예약 작업이 새 분석을 시작하지 않는다. 결제와 시작은 사용자의 행동이며, 서버는 이미 시작된 것을 끝낼 뿐이다.
- 알림을 늘리지 않는다. 완료 이메일 하나로 유지한다.

## 10. 롤백

라우트와 스케줄러 설정을 제거하면 이전 동작(브라우저 폴링 전용)으로 돌아간다. 데이터베이스 함수와 저장 형식은 바뀌지 않으므로 진행 중인 실행도 영향을 받지 않는다.
