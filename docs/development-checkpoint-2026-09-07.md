# MOOA Resume 개발 체크포인트

기준일: 2026-09-18 (현재 체크포인트 파일명 유지)
마지막 갱신: **하이브리드 앱 1차 구현 완료(로컬)**. 기존 TWA(`com.mooaresume.twa`)의 시작 주소를 새 앱 전용 웹 화면 `/app`으로 돌리고, 입력·결제·분석은 기존 웹 구현을 그대로 재사용한다. Google Play 결제 경로의 구매 소비·미완료 구매 복구·재시도 영구 실패·KR 외 결제 문제를 고쳤다. 실기기 실행과 실제 Play 구매는 미검증이며, 다음 작업은 `/app` 배포 → TWA 재빌드 → 내부 테스트 트랙이다. 법률 출시 검토의 미해결 사항은 그대로 남아 있다.

### 가장 큰 미검증 위험

**AI 생성을 실제로 한 번도 돌려보지 않았다.** 타입·테스트·빌드는 통과했고 프롬프트와 스키마는 갖춰졌지만, 실제 모델 응답으로 쓸 만한 문서가 나오는지는 **아무도 확인하지 않았다.** 값을 받기 전에 각 문서 종류마다 최소 한 건씩 실제로 돌려 보고 결과를 읽어야 한다.

### 법률을 팔면 안 되는 이유

프롬프트 상한이 6만 자(약 40쪽)다. 300쪽 플랜을 99,000원에 팔면서 앞 40쪽만 읽는다. 화면이 그 사실을 세 곳에서 말하도록 해 두었지만(결제 단추 위·결과·업로드), **말하는 것과 읽는 것은 다르다.**

## 이 브랜치에 포함된 것

### 취업 서류

- **경력기술서**(`/career-description`) — 이력서·자소서·자격증을 올리면 회사별 경력으로 정리. 직무기술서(JD)와는 다른 문서로 갈라 놓았고, JD 분석은 자소서 첨삭(PRO)으로 보낸다.
- **포트폴리오 설명글**(`/portfolio`) — 프로젝트마다 소개·역할·문제·실행·성과·기술 + 전체 목차. 입력이 프로젝트 카드 반복인 유일한 도구다(한 칸에 몰아 적으면 A의 성과가 B에 붙는다). 목차는 모델이 적은 것을 버리고 결과 목록에서 다시 만든다.

### 법률 사건 워크스페이스

- 사건 단위로 자료가 쌓이고, 같은 자료로 문서를 하나씩 만든다. **연속성은 강제가 아니다** — 항소장 하나만 필요하면 사건 만들고 그것만 결제하면 된다.
- 문서 10종이 설정표 하나(`legalDocumentDefinitions`)와 출력 스키마 하나를 공유한다. 종류마다 고유 지시문(3~5줄)이 있고, 내 지위(원고/피고)에 따라 순서가 바뀐다.
  - 사건부터 이해하기: 사건 분석·주요쟁점
  - 소송 전: 내용증명
  - 1심: 소장 · 답변서 · 준비서면 · 증거정리 · 상대방 서면 반박
  - 판결 후: 판결문 분석 · 항소장 · 항소이유서
- **취업 쪽과 반대로 자료를 저장한다** — 사건은 저장이 곧 기능이다. RLS로 본인만, 사건 삭제 시 cascade, `noindex`, 로그에 내용 미기록.
- 안전 규칙: 기한 계산 금지, 승소 확률 금지, 조문·판례 지어내기 금지, 고지 문구는 코드가 붙임.

### 안전장치 다섯 겹

1. 페이지 상한 (플랜: 300/700/1,500쪽)
2. 파일 수 상한 (100/200/400개)
3. 압축 해제 후 용량 상한 (1/2/4GB)
4. 한 요청 토큰 상한 (272K 넘으면 단가가 뛰므로 200K 안전선에서 분할)
5. **주문당 API 원가 차단기 8,000원** — 부르기 전에 최악으로 재고, 7,000원 넘으면 비싼 경로부터 닫는다

판정은 AND다. 하나라도 넘으면 그 플랜을 벗어난다. **ZIP은 압축 크기가 아니라 푼 뒤 실제 분량으로 판정한다.** 값은 서버가 저장된 자료를 다시 재서 정한다.

### 분석 매커니즘

- 모델을 역할로 나눴다: SCAN(훑기) → REVIEW(검토) → FINAL(작성). 이름은 환경변수라 모델이 바뀌어도 코드는 그대로다.
- **서면 작성 단계에 자료 전체를 넣으면 호출 전에 거부한다.** 이 서비스에서 가장 비싼 실수라 검사로 막았다.
- 예산이 빠듯하면 급을 한 단계 내린다. 다 쓰면 호출 자체를 멈춘다.
- 건당 원가를 `legal_document_builds`에 남긴다(토큰·금액·급·모델·쪽수). 원가를 모르면 `null` — 0으로 적으면 "공짜였다"가 되어 합계가 낮아진다.

### 읽기 엔진 정책

- 텍스트 있는 쪽은 공짜 추출 → 스캔은 Upstage OCR → 흐리면 Parse Standard 승격(예산 받쳐 줄 때만) → Enhanced는 기본 닫힘 → 사진 증거만 OpenAI Vision.
- **한 쪽은 한 엔진만 읽는다.** 중복 과금을 불변식으로 못박고 테스트로 고정했다.
- `READING_PROVIDER=OPENAI` 한 줄로 갈아탄다. 키가 없으면 자동으로 OpenAI 경로로 내려간다.
- **정책만 있고 실제 Upstage HTTP 호출부는 없다.** 키가 없어 테스트할 수 없었다.

### 공통 뼈대 (네 번째 복사본을 만들 차례에 빼냄)

`build-lifecycle.ts`(결제 수명주기) · `document-build-checkout.ts`(Polar) · `document-build-model.ts`(Responses 호출) · `request-guards.ts`(출처·로그인) · `document-build-tool.module.css`(세 도구 공용).

**이력서 제작(`resume-build*`)은 옮기지 않았다.** 이미 팔고 있는 결제 경로라 정리 이득만으로 건드리지 않았다.

## 하이브리드 앱 재개 (09-18 갱신 — 다음 주 아래 순서 우선)

클로드에게 넘길 시작 문서: [하이브리드 앱 인계](claude-hybrid-app-handoff-2026-09-18.md). 요구·읽을 파일·작업 순서·결제/보존 경계를 모았다. 이 체크포인트는 계속 현재 재개 기준이다.

### 사용자 확정 방향

- 기존 웹의 취업 관련 기능을 모두 재사용한다. 별도 앱에서 기능을 축소하거나 동일 기능을 따로 재구현하는 방향은 폐기한다. 커뮤니티 제외 등 기존 앱 제품 범위는 유지한다.
- 앱을 켜면 바로 넓은 간편 첨삭 입력창. 홈과 첨삭을 나누지 않는다. 하단 메뉴바와 모바일 입력·이동 최적화는 유지한다.
- 상단 QUICK / PRO / FINAL 선택과 각 서비스의 작성 유형 설정을 제공한다. 기존 상품 범위와 FINAL 활성화 조건을 그대로 존중한다.
- 기존 웹처럼 파일 첨부, 여러 자료 추가, 서류 분류 확인/수정, 문항 구분과 글자 수/목표 글자 수 설정을 제공한다. TXT 전용 앱으로 제한하지 않는다. 웹에서 실제 지원하는 형식과 제한을 먼저 확인하며 HWP/OCR 등 없는 기능까지 지원한다고 말하지 않는다.
- 입력 시작 시 지원서 이름을 요구하지 않는다. 저장 때 자동 이름 또는 선택 입력 방향이다.
- 사용자는 결제 질문에 **“Google Play 결제까지 연결”**을 명시 선택했다. 단순 결제 보류로 기록하지 않는다. 연결 구현은 승인됐지만 실제 유료 구매·AI 호출·프로덕션 배포·스토어 공개 승인은 별개다.

### 현재까지 확인한 것과 미완료

- 기존 `src/components/pro-input-page.tsx`는 기본 `SIMPLE` 입력이며 `simple-intake.tsx`의 다중 첨부·분류와 `simple-intake-mapping`의 문항/길이 처리를 사용한다. 상세 입력과 CREATE / BUILD / POLISH도 기존 웹에 있다.
- `resume-intake.tsx`는 PDF / DOCX / TXT / MD 추출과 문항 구분, 공백 제외 글자 수를 제공한다. `local-document.ts`에는 ZIP 해제도 있지만 실제 업로드 경로별 허용 형식은 다르므로 일괄 지원이라고 단정하지 않는다.
- 웹 결제는 `src/lib/google-play/purchase.ts`의 TWA Digital Goods API 분기와 기존 Polar 분기가 있다. `application-case-handoff.tsx`는 구매 토큰을 서버 검증한 후 분석을 시작한다. 네이티브 `/api/mobile/billing`은 Bearer 인증과 계정/분석 건 구매 바인딩을 사용한다. 웹 쿠키 로그인과 네이티브 구매의 연결 방식을 아직 결정·구현하지 않았다.
- WebView/TWA 등 최종 래퍼 선택, 앱 전용 공유 웹 화면, 로그인/뒤로가기/첨부/내보내기 및 결제 브리지는 **미구현**이다. iframe 방식 등 검토 중 아이디어를 확정 아키텍처로 오해하지 않는다.
- `apps/mobile`에서 `npm install react-native-webview`를 시도했으나 사용자 중단 요청으로 종료했다. 확인한 `package.json`에는 해당 의존성이 없으며 설치 완료로 취급하지 않는다. 재개 시 package-lock 및 설치 상태를 확인한다.
- `http://127.0.0.1:8089/`에 보였던 화면은 기존 네이티브 시안의 Expo 웹 미리보기다. 다음 주 서버가 종료돼 있을 수 있다. 하이브리드 화면으로 변경됐다고 안내하지 않는다.
- 이전 시안 검증: 웹/앱 타입 검사 통과, lint 오류 0/기존 경고 2, 149개 파일/1,172개 테스트 통과, Next build/Expo export/Android APK 빌드 통과. 실제 기기 로그인·실구매·환불·유료 AI·원격 RLS E2E는 미검증. 이 결과를 새 하이브리드 버전의 검증으로 사용하지 않는다.

## 후속 개발 backlog (과거 계획, 위 우선순위 뒤에 진행)

### 1. 대용량 파이프라인 — 여러 출시 차단 항목 중 하나

```
업로드 → 압축 해제 → 페이지 분해 → 읽기 → 페이지별 저장(쪽번호 보존)
     → 타임라인·쟁점·증거 색인 → 필요한 20~100쪽만 상위 모델 재검토 → 결과
```

**쪽번호를 절대 버리면 안 된다.** 결과에서 원문으로 되돌아갈 수 있어야 한다(진료기록 p.317 형태). 지금 `evidence` 필드가 그 방향인데 파일명까지만이고 쪽수가 없다.

### 2. 실제 AI 생성 검증

문서 10종마다 최소 한 건씩 실제로 돌려 결과를 읽는다. 프롬프트 손볼 곳이 반드시 나온다.

### 3. Upstage 호출부 + 이미지 업로드

키를 넣은 뒤. 지금은 PDF·DOCX·TXT·ZIP만 받고 사진은 아예 못 올린다(자격증·카톡 캡처·계약서 사진이 전부 막혀 있다).

### 4. 값 결정과 Polar 상품

09-12 검토 당시 로컬 `POLAR_LEGAL_PRODUCT_ID`는 없었다. 운영 환경/대시보드 상품 존재 여부는 미확인. 취업 가격과 상품 설정에는 별도 작업 변경이 있으므로 현재 코드를 재확인한다.

### 5. 관리자 화면에 원가 표시

데이터는 이미 쌓이게 해 두었다. 50~100건 뒤에 300쪽 상한과 벤더 선택을 숫자로 다시 본다.

## 로컬에서 확인하는 법

먼저 실행 중인 `http://localhost:3000/legal`을 확인한다. 서버가 없을 때 현재 브랜치에서 `npm.cmd run dev`를 실행한다. 새 서버를 중복 실행하거나 다른 작업자의 서버를 종료하지 않는다.

검증 명령: `npm.cmd run typecheck`, `npm.cmd run lint`, `npm.cmd run test`, 필요 시 `npm.cmd run build`. 원격 migration은 자동 적용하지 않는다. 이번 종료 작업은 문서 갱신만 했으므로 전체 테스트를 반복하지 않았다.
