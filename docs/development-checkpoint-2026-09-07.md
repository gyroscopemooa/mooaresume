# MOOA Resume 개발 체크포인트

기준일: 2026-09-07
마지막 갱신: 서류 3종(경력기술서·포트폴리오·법률 사건)을 미리보기 상태로 완성. 법률은 대용량 처리 전까지 판매 불가.

이 문서가 현재 재개 기준이다. `docs/development-checkpoint-2026-08-21.md`의 미해결 항목(QUICK 입력 확인 버튼, 실제 결제 분석 복구, 결과 비교 선택)은 **이 브랜치에서 건드리지 않았고 여전히 열려 있다** — `main` 쪽 일이므로 그 문서를 함께 봐야 한다.

## 현재 상태

- 작업 브랜치: `claude/job-description-input-attach-cx44pf` (`origin/main`보다 8커밋 앞섬, 충돌 없이 fast-forward 가능)
- **병합·배포하지 않았다.** 프로덕션 Supabase migration도 적용하지 않았다.
- 실제 결제와 OpenAI 호출은 한 번도 실행하지 않았다.
- 새 서류 3종은 전부 `preview` 상태 — 드로어 목록에 안 나오고 `noindex`다. 주소를 직접 치면 열린다.

## 완성도

| 영역 | 완성도 | 판매 가능 |
|---|---:|---|

### 가장 큰 미검증 위험

**AI 생성을 실제로 한 번도 돌려보지 않았다.** 타입·테스트·빌드는 통과했고 프롬프트와 스키마는 갖춰졌지만, 실제 모델 응답으로 쓸 만한 문서가 나오는지는 **아무도 확인하지 않았다.** 값을 받기 전에 각 문서 종류마다 최소 한 건씩 실제로 돌려 보고 결과를 읽어야 한다.

### 법률을 팔면 안 되는 이유

프롬프트 상한이 6만 자(약 40쪽)다. 300쪽 플랜을 99,000원에 팔면서 앞 40쪽만 읽는다. 화면이 그 사실을 세 곳에서 말하도록 해 두었지만(결제 단추 위·결과·업로드), **말하는 것과 읽는 것은 다르다.**

## 이 브랜치에 포함된 것

### 취업 서류

- **경력기술서**(`/career-description`) — 이력서·자소서·자격증을 올리면 회사별 경력으로 정리. 직무기술서(JD)와는 다른 문서로 갈라 놓았고, JD 분석은 자소서 첨삭(PRO)으로 보낸다.
- **포트폴리오 설명글**(`/portfolio`) — 프로젝트마다 소개·역할·문제·실행·성과·기술 + 전체 목차. 입력이 프로젝트 카드 반복인 유일한 도구다(한 칸에 몰아 적으면 A의 성과가 B에 붙는다). 목차는 모델이 적은 것을 버리고 결과 목록에서 다시 만든다.

### 법률 사건 워크스페이스

- 사건 단위로 자료가 쌓이고, 같은 자료로 문서를 하나씩 만든다. **연속성은 강제가 아니다** — 항소장 하나만 필요하면 사건 만들고 그것만 결제하면 된다.
- 문서 10종이 설정표 하나(`legalDocumentDefinitions`)와 출력 스키마 하나를 공유한다. 종류마다 고유 지시문(3~5줄)이 있고, 내 지위(원고/피고)에 따라 순서가 바뀐다.
  - 사건부터 이해하기: 사건 분석·주요쟁점
  - 소송 전: 내용증명
  - 1심: 소장 · 답변서 · 준비서면 · 증거정리 · 상대방 서면 반박
  - 판결 후: 판결문 분석 · 항소장 · 항소이유서
- **취업 쪽과 반대로 자료를 저장한다** — 사건은 저장이 곧 기능이다. RLS로 본인만, 사건 삭제 시 cascade, `noindex`, 로그에 내용 미기록.
- 안전 규칙: 기한 계산 금지, 승소 확률 금지, 조문·판례 지어내기 금지, 고지 문구는 코드가 붙임.

### 안전장치 다섯 겹

1. 페이지 상한 (플랜: 300/700/1,500쪽)
2. 파일 수 상한 (100/200/400개)
3. 압축 해제 후 용량 상한 (1/2/4GB)
4. 한 요청 토큰 상한 (272K 넘으면 단가가 뛰므로 200K 안전선에서 분할)
5. **주문당 API 원가 차단기 8,000원** — 부르기 전에 최악으로 재고, 7,000원 넘으면 비싼 경로부터 닫는다

판정은 AND다. 하나라도 넘으면 그 플랜을 벗어난다. **ZIP은 압축 크기가 아니라 푼 뒤 실제 분량으로 판정한다.** 값은 서버가 저장된 자료를 다시 재서 정한다.

### 분석 매커니즘

- 모델을 역할로 나눴다: SCAN(훑기) → REVIEW(검토) → FINAL(작성). 이름은 환경변수라 모델이 바뀌어도 코드는 그대로다.
- **서면 작성 단계에 자료 전체를 넣으면 호출 전에 거부한다.** 이 서비스에서 가장 비싼 실수라 검사로 막았다.
- 예산이 빠듯하면 급을 한 단계 내린다. 다 쓰면 호출 자체를 멈춘다.
- 건당 원가를 `legal_document_builds`에 남긴다(토큰·금액·급·모델·쪽수). 원가를 모르면 `null` — 0으로 적으면 "공짜였다"가 되어 합계가 낮아진다.

### 읽기 엔진 정책

- 텍스트 있는 쪽은 공짜 추출 → 스캔은 Upstage OCR → 흐리면 Parse Standard 승격(예산 받쳐 줄 때만) → Enhanced는 기본 닫힘 → 사진 증거만 OpenAI Vision.
- **한 쪽은 한 엔진만 읽는다.** 중복 과금을 불변식으로 못박고 테스트로 고정했다.
- `READING_PROVIDER=OPENAI` 한 줄로 갈아탄다. 키가 없으면 자동으로 OpenAI 경로로 내려간다.
- **정책만 있고 실제 Upstage HTTP 호출부는 없다.** 키가 없어 테스트할 수 없었다.

### 공통 뼈대 (네 번째 복사본을 만들 차례에 빼냄)

`build-lifecycle.ts`(결제 수명주기) · `document-build-checkout.ts`(Polar) · `document-build-model.ts`(Responses 호출) · `request-guards.ts`(출처·로그인) · `document-build-tool.module.css`(세 도구 공용).

**이력서 제작(`resume-build*`)은 옮기지 않았다.** 이미 팔고 있는 결제 경로라 정리 이득만으로 건드리지 않았다.

## 남은 일 (우선순위)

### 1. 대용량 파이프라인 — 법률 출시 전 마지막 관문

```
업로드 → 압축 해제 → 페이지 분해 → 읽기 → 페이지별 저장(쪽번호 보존)
     → 타임라인·쟁점·증거 색인 → 필요한 20~100쪽만 상위 모델 재검토 → 결과
```

**쪽번호를 절대 버리면 안 된다.** 결과에서 원문으로 되돌아갈 수 있어야 한다(진료기록 p.317 형태). 지금 `evidence` 필드가 그 방향인데 파일명까지만이고 쪽수가 없다.

### 2. 실제 AI 생성 검증

문서 10종마다 최소 한 건씩 실제로 돌려 결과를 읽는다. 프롬프트 손볼 곳이 반드시 나온다.

### 3. Upstage 호출부 + 이미지 업로드

키를 넣은 뒤. 지금은 PDF·DOCX·TXT·ZIP만 받고 사진은 아예 못 올린다(자격증·카톡 캡처·계약서 사진이 전부 막혀 있다).

### 4. 값 결정과 Polar 상품

경력기술서·포트폴리오 값이 자리표시값(7,900)이다. Polar 상품 3개 미생성.

### 5. 관리자 화면에 원가 표시

데이터는 이미 쌓이게 해 두었다. 50~100건 뒤에 300쪽 상한과 벤더 선택을 숫자로 다시 본다.

## 재개할 때 보호해야 할 것

- **이력서 제작·자소서 첨삭(QUICK/PRO/FINAL) 경로를 건드리지 않는다.** 이미 팔고 있다.
- 새 서류 3종의 `preview` 상태를 임의로 `available`로 바꾸지 않는다 — 사용자가 확인 후 결정한다.
- 법률의 안전 규칙(기한 계산 금지·승소 확률 금지·고지 문구)을 프롬프트에서 빼지 않는다.
- 값은 `builder-pricing.ts`와 `case-intake-limits.ts`의 `CASE_PLANS` 두 곳에만 있다. 같은 값을 세 번째 자리에 복사하지 않는다.
