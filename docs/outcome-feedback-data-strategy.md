# 지원 결과 피드백 및 데이터 축적 전략

작성일: 2026-08-16  
상태: 제품·개인정보 설계안. 실제 수집 전 법률 및 개인정보 전문가 검토 필요.

## 결론

지원 결과 데이터는 장기적인 제품 경쟁력이 될 수 있다. 다만 원본 지원서 파일을 무기한 쌓는 방식은 피하고, 서비스 제공용 원본·사용자 대시보드용 구조화 데이터·제품 개선용 가명 데이터를 분리한다.

파일을 삭제하고 학점, 회사, 직무, 경력과 결과만 남겨도 조합에 따라 개인을 알아볼 수 있으므로 자동으로 익명정보가 되는 것은 아니다.

## 데이터 세 층

### 1. Service Data

현재 지원 건 처리와 결과 재열람에 필요한 데이터.

- 업로드 원본
- 추출 텍스트
- 지원 회사와 직무
- 생성 결과
- 사용자 수정본

보관 기간과 삭제 시점을 서비스 시작 전에 명시한다. 원본은 결과 제공에 필요한 최소 기간만 보관하고 사용자가 즉시 삭제할 수 있게 한다.

### 2. User Dashboard Data

사용자가 자신의 지원 이력을 관리하기 위한 구조화 스냅샷.

- 학력 수준 및 전공
- 학점과 기준 만점
- 어학시험 종류·점수·취득 시점
- 경력 기간과 직무 범주
- 자격증
- 해외 경험 유형과 기간
- 지원 회사·직무·채용 시기
- 사용한 경험과 지원서 버전

원본 문서와 분리하고, 각 필드에 출처·확인 상태·사용자 수정 이력을 둔다.

### 3. Product Improvement Data

제품 분석과 평가 개선에 필요한 최소한의 가명 데이터.

- 가명 case ID
- 범주화된 스펙
- 공고 요구사항 범주
- 사용한 경험 범주
- 내부 분석 feature version
- 지원 단계와 결과
- 결과 신뢰도

이름, 이메일, 전화번호, 주소, 생년월일, 원본 파일명, 원문 자유서술과 직접 식별자는 제외한다. 원본 case와 연결하는 키는 별도 접근 통제 영역에 보관한다.

## 지원 결과 상태

- NOT_APPLIED
- APPLIED
- SCREENING_REJECTED
- INTERVIEW
- FINAL_INTERVIEW
- OFFERED
- HIRED
- WITHDRAWN
- NO_RESPONSE
- UNKNOWN

단순 합격/불합격만 저장하면 어느 단계에서 탈락했는지 알 수 없으므로 채용 단계를 구분한다.

## 결과 수집 UX

권장 알림:

- 지원 예정일 또는 제출일에 상태 확인
- 제출 14일 후
- 제출 30일 후
- 필요 시 60일 후 마지막 확인

질문은 짧게 유지한다.

1. 실제로 제출했나요?
2. 현재 어디까지 진행됐나요?
3. 결과 통보를 받았나요?
4. 이번 결과에서 도움이 됐거나 부족했던 점이 있나요?

## 보상과 거짓 응답 방지

쿠폰은 합격 여부가 아니라 설문 완료에 동일하게 제공한다. 합격자에게만 큰 보상을 주면 거짓 합격과 불합격 미응답이 늘어난다.

- 합격·불합격·진행 중 모두 같은 기본 보상
- case ID당 동일 단계 설문 1회
- 제출 시점과 설문 가능 기간 제한
- 모순 응답은 자동 확정하지 않고 확인 상태
- 짧은 시간에 반복 제출하는 계정 제한
- 보상과 분석 데이터의 신뢰도는 분리

증빙은 필수로 만들지 않는 것이 우선이다. 선택적 증빙을 도입한다면 회사명·지원자명·연락처 등 불필요한 부분을 가리도록 안내하고, 검증 후 원본을 즉시 삭제하는 별도 정책이 필요하다.

## 결과 신뢰도

- SELF_REPORTED: 사용자가 한 번 응답
- FOLLOWUP_CONFIRMED: 다른 시점에 같은 상태를 재확인
- DOCUMENT_VERIFIED: 선택적 증빙으로 확인
- INCONSISTENT: 이전 응답과 충돌

자가응답은 버리지 않되 검증된 결과와 같은 가중치로 학습·평가하지 않는다.

## 대시보드 활용

사용자에게는 다음 가치를 제공한다.

- 지원 회사별 진행 상태
- 사용한 자기소개서와 경험
- 제출 당시 스펙 스냅샷
- 면접까지 이어진 지원서의 공통점
- 반복적으로 부족했던 역량과 근거

내부에서는 개인의 합격 가능성을 단정하지 않고 집단 수준에서 모델과 루브릭을 평가한다.

## 분석 시 주의

“이 학력·스펙이면 합격”처럼 인과관계로 해석하지 않는다. 회사, 직무, 시기, 채용 규모, 경력 수준과 자기선택 편향이 함께 작용한다.

- 합격 확률을 사용자에게 표시하지 않는다.
- 학교명·성별·나이 등으로 차별적 추천을 만들지 않는다.
- 작은 집단 통계는 노출하지 않는다.
- 통계는 최소 표본 기준과 신뢰 구간을 둔다.
- 모델 개선 전 편향·누락·대표성 검사를 한다.
- 자유서술 원문보다 구조화된 특징과 평가 오류를 우선 사용한다.

## 개인정보 및 동의 UX

서비스 이용 동의와 제품 개선용 데이터 활용 선택을 분리한다.

- 필수: 서비스 제공을 위한 처리
- 선택: 가명화된 제품 개선 및 통계 활용
- 선택: 결과 확인 알림
- 선택: 사례 공개

사례 공개 동의는 제품 개선 동의와 별개다. 사용자가 동의를 철회하거나 삭제를 요청할 수 있는 경로를 제공한다.

개인정보보호법상 가명정보는 통계작성·과학적 연구 등에 활용할 수 있지만 가명처리 절차, 위험성 검토, 적정성 검토와 안전한 관리가 필요하다. 본 문서는 법률 자문을 대체하지 않는다.

## 권장 구현 순서

1. Application Case와 제출 상태 모델

4. 결과 신뢰도
5. 원본 삭제와 구조화 데이터 분리
6. 가명 분석 데이터셋 생성 작업
7. 최소 표본 기반 내부 리포트
8. 실제 결과를 활용한 eval 및 rubric 보정

## 현재 결정

지금은 Supabase 저장이나 실제 설문 발송을 연결하지 않는다. 먼저 데이터 계약과 개인정보 경계를 고정한다.

## 최신 기준 문서

루트 MOOA_RESUME_OUTCOME_DATA_FLYWHEEL_ADDENDUM.md를 Outcome 및 Snapshot 설계의 최신 Source of Truth로 사용한다. 이 docs 문서는 Codex 구현 기록과 개인정보 경계 요약이다.

## 2026-08-16 추가 구현

- Candidate Snapshot과 현재 프로필을 분리했다.
- Job Snapshot을 지원 당시 공고 기준으로 고정할 수 있게 했다.
- Application Snapshot에 원문, AI 수정본, 사용 경험과 버전 메타데이터를 연결했다.
- User Final이 실제 제출본이라는 가정을 금지했다.
- Submission Snapshot은 사용자가 “이 버전으로 제출”을 확인한 경우에만 생성하도록 계약을 분리했다.
- Outcome을 stage와 result로 분리했다.
- Outcome은 특정 Submission Snapshot을 참조할 수 있게 했다.
- UNKNOWN, PENDING, NOT_SUBMITTED를 정상 상태로 취급한다.

## 홈페이지 카피 단계

### 데이터 축적 전

“실제 지원 결과에서 배우는 서비스를 만듭니다”처럼 구조와 방향을 설명한다. 이미 대규모 데이터를 분석 중인 것처럼 표현하지 않는다.

### 데이터 축적 후

최소 표본·대표성·동의·가명처리 검토를 통과한 뒤에만 “축적된 지원 결과를 바탕으로 분석 기준을 개선합니다”라고 표현한다.

### 검증 가능한 규모 확보 후

집계 방식과 포함 기준을 공개할 수 있을 때 실제 사례 수를 표시한다. 단순 가입 건수나 분석 실행 횟수를 Outcome 사례 수처럼 사용하지 않는다.
