# MOOA Resume — BUILD 모드 채우기 결정

> 결정일: 2026-08-22
> 상태: 최신 제품 결정
> 관련 문서: `docs/create-mode-and-pricing-decision.md`, `docs/analysis-consistency-and-rounded-editing-philosophy.md`, `docs/pricing-unit-economics-and-input-limits.md`, `MOOA_RESUME_PROJECT_SPEC.md`
> 우선순위: 동일 항목이 충돌하면 이 문서의 결정이 우선한다. 기존 문서는 수정하지 않는다.

## 1. 배경 — 지금 아무도 채워주지 않는다

사용자가 실제로 마주치는 상태는 이렇다.

- 기업이 요구한 글자 수는 700자인데 300자만 썼다.
- 문항 4개 중 하나를 비워 뒀다.
- 몇 줄만 써 놓고 나머지를 채우고 싶다.

지금 시스템은 이 세 경우 모두 **아무것도 채워주지 않는다.** 우연이 아니라 세 곳에 명시적으로 박혀 있는 정책이다.

```
prompt.ts   "원문의 정보량이 부족하면 억지로 분량을 채우지 말고 확인 질문을 남기세요"
prompt.ts   "아직 작성되지 않은 문항은 revisions에 넣지 마세요"
questions.ts .filter((question) => question.answer.trim())
```

그 결과 BUILD(내용 보완)와 POLISH(최종 첨삭)의 동작이 사실상 같아졌다. 이름은 "내용 보완"인데 보완을 하지 않으므로 BUILD의 자리가 애매해진 것이 현재 문제의 본질이다.

## 2. 결정 — 세 유형을 실제로 다르게 만든다

```
1유형 CREATE   백지        사실을 단계별로 받아 초안 작성      (구현됨, 이번에 건드리지 않음)
2유형 BUILD    반쯤 작성   빈 문항과 부족한 분량을 채움        (이번 작업 대상)
3유형 POLISH   거의 완성   다듬기만, 채우지 않음               (현재 동작 유지, 건드리지 않음)
```

POLISH는 이미 원하는 동작을 하고 있으므로 **옮기거나 복제하지 않는다.** BUILD만 바꾸면 세 유형이 자동으로 갈라진다.

## 3. 채우기 규칙 — 빈칸을 없애는 방법은 지어내기가 아니다

최종 첨삭본은 빈칸 없이 완결된 글이어야 한다. 빈칸투성이 결과물은 유료 산출물로 성립하지 않는다.

동시에 없는 사실을 만들 수도 없다. 이 둘은 충돌하지 않으며, 해법은 이미 프롬프트에 있는 규칙이다.

> "수치가 없으면 정성적 행동과 확인 가능한 변화만 활용하세요. 임의의 숫자를 추가하지 마세요."

즉 **수치·고유명사·검증 불가 사실은 넣지 않되 문장은 완결시킨다.**

| | 예시 | 판정 |
|---|---|---|
| 지어낸 수치 | "고객 후기 500건을 분석해 5가지 요인을 도출했습니다" | 금지. 면접에서 방어 불가 |
| 빈칸 노출 | "고객 후기 [몇 건]을 분석해…" | 최종 첨삭본에는 부적합 |
| 수치 없이 완결 | "고객 후기를 유형별로 분류해 반복되는 불편 사항을 정리했습니다" | **채택** |

채우는 문장은 **행동·과정·태도·배운 점** 중심으로 쓴다. 이 범주는 지원자의 기존 서술에서 도출할 수 있고 수치 검증이 필요 없다.

### 3-1. 채우기의 재료 순서

첫 구현은 "원문의 사실 범위 안에서" 늘리라고만 했다. 그 결과 표현만 바뀌고 내용은 하나도 늘지 않았으며, 오히려 원문의 구체적 수치가 빠져 540자가 503자로 줄었다. 표현을 다듬는 것은 채우기가 아니다.

```
1순위  원문에 이미 있는 경험을 더 구체적으로 푼다
2순위  지원자료(이력서·경력기술서·포트폴리오·추가 경험)에서
       이 문항과 관련 있는데 아직 쓰이지 않은 사실을 가져온다
3순위  둘 다 없으면 멈추고, 무엇을 더 알려주면 채울 수 있는지 남긴다
```

**2순위가 진짜 채우기다.** 이력서에 적힌 사실은 지원자가 직접 밝힌 것이므로 가져다 쓰는 것이 창작이 아니며, 면접에서도 방어된다. PRO가 그 자료를 받는 이유가 바로 이것이다. 다만 자료에 없는 내용을 추측해 덧붙이는 것은 여전히 금지한다.

원문에 있던 수치와 고유명사(대회 규모, 순위, 기간, 자격증 이름)는 첨삭 과정에서 빼지 않는다. 지원서에서 가장 검증 가능한 근거이기 때문이다.

## 4. 표시 — 화면과 복사본의 역할을 나눈다

| 화면 | 채운 부분의 표시 |
|---|---|
| 문항별 첨삭 | 원문과 **다른 색 + 확인 필요 표시**. 무엇을 검토해야 하는지 보이게 한다 |
| 최종 첨삭본 | **완결된 문장**. 빈칸도 대괄호 표기도 없다 |

복사·다운로드는 **제안을 빼지 않는다.**

초안에서 채운 부분을 덜어내면 다시 미완성 글이 되고, 그것은 이 기능을 만든 이유를 스스로 무효화한다. 최종 첨삭본은 그대로 제출할 수 있는 상태여야 한다.

대신 최종 첨삭본 상단에 **채운 제안이 포함되어 있다는 사실과 어디서 확인할 수 있는지**를 고정 문구로 알린다.

> 비어 있던 부분을 채운 제안이 포함되어 있습니다. 어디를 채웠는지는 문항별 첨삭에서 색으로 확인할 수 있습니다. 제출 전에 사실과 맞는지 확인해 주세요.

책임 소재는 복사 버튼을 나누는 것이 아니라 **§3의 채우기 규칙**이 진다. 없는 수치와 고유명사를 애초에 만들지 않으므로, 사용자가 그대로 제출해도 거짓 사실이 들어가지 않는다. 표시는 더 정확하게 고칠 기회를 주기 위한 것이지 제출을 막기 위한 장치가 아니다.

*(초기 안은 "기본 복사 = 확인된 내용만 / 제안 포함은 별도 버튼"이었으나, 최종 첨삭본이 빈칸 없이 완결되어야 한다는 결정과 충돌하여 위와 같이 대체한다.)*

## 5. 채우기를 허용하는 조건 — 문항 구분이 되어 있어야 한다

자기소개서를 문항 구분 없이 한 덩어리로 붙여넣은 경우(`splitCoverLetterDraft`가 제목·질문이 비어 있는 단일 문항 하나만 반환하는 상태)에는 채우기를 제공하지 않는다.

이유는 두 가지다.

1. 어느 문항에 무엇이 부족한지 판단할 근거가 없다. 목표 글자 수도 문항 단위로만 의미가 있다.
2. 한 덩어리 전체를 늘리면 분량 제어가 불가능해진다.

이 경우 **결제로 진행할 수 없게 막는다.** 처음에는 경고만 띄우고 진행을 허용했으나, 실제 테스트에서 세 가지가 동시에 잘못되는 것이 확인됐다.

1. 문항별 목표 글자 수가 없어 기본값(700자)이 자소서 전체에 적용된다. 2,000자짜리 글이 700자를 목표로 측정된다.
2. 어느 문항이 짧은지 알 수 없어 채우기가 아예 동작하지 않는다.
3. 문항별 첨삭이 한 덩어리로 뭉쳐 나온다.

셋 다 사용자가 버튼 한 번(`문항 구분 확인하기`)으로 해결할 수 있는 문제이므로, 결제 전에 그 한 번을 요구하는 편이 낫다.

## 6. 분량 상한 — 입력에만 있고 출력에는 없었다

`docs/pricing-unit-economics-and-input-limits.md`는 입력 hard cap(10,000~12,000자)만 정하고 **출력 상한을 정하지 않았다.** 채우기를 도입하면 출력이 늘어나므로 상한이 필요하다.

문항마다 `targetLength`가 이미 있으므로 별도 설정을 만들지 않는다.

```
문항별 상한   targetLength × 1.15   (검증기의 LENGTH_OVER 기준과 동일)
전체 상한     Σ targetLength × 1.15
```

목표 글자 수를 채울 근거가 없으면 **억지로 채우지 않는다.** 다만 지금처럼 침묵하지 않고 "이 문항은 무엇을 더 알려주시면 채울 수 있다"를 남긴다. 분량을 맞추려고 물을 타는 것은 첨삭이 아니라 훼손이다.

## 7. 가격 — 세 유형 모두 같은 PRO 가격

`docs/create-mode-and-pricing-decision.md` §7의 결정을 그대로 따른다.

> 가격은 대화 시간이나 메시지 수가 아니라 **완성 범위**를 기준으로 한다.
> PRO = 기업 지원서 한 건의 전체 코칭

유형별 차등 가격을 만들지 않는 이유:

1. 사용자는 자신이 어느 유형인지 모른다. 가격이 다르면 그 판단이 돈 결정이 되어 이탈로 이어진다.
2. 유형은 `decideWritingMode`가 자동으로 정한다. 시스템이 정한 것을 가격으로 차등하면 "왜 나는 비싼 쪽인가"가 된다.
3. 가격이 다르면 사용자가 싼 유형을 고르고 "왜 안 채워주냐"고 묻게 된다.
4. 비용 차이가 작다. 문항당 400자 추가, 문항 4개면 약 1,600자로 PRO 한 건에서 큰 비중이 아니다.

**새 상품도 새 결제 단계도 만들지 않는다.**

## 8. 기존 문서에서 갱신되는 항목

### 8-1. 갱신 — QUICK의 BUILD 범위

`docs/create-mode-and-pricing-decision.md` §2의 다음 항목:

```text
QUICK
- BUILD 또는 POLISH 이용 가능
- 작성 중인 글의 내용 보완
```

여기서 "내용 보완"의 의미를 이 문서가 좁힌다.

```text
QUICK  · BUILD  = 부족한 부분을 지적하고 무엇을 보완해야 하는지 알려준다 (채우지 않는다)
PRO    · BUILD  = 빈 문항과 부족한 분량을 실제로 채운다
```

QUICK에서 BUILD를 선택할 수 있다는 결정 자체는 유지한다. 채우기 실행만 PRO 전용으로 둔다. 채우기는 지원자료 교차분석이 있어야 사실에 가깝게 채울 수 있고, 그 교차분석이 이미 PRO 전용이기 때문이다.

**결제 전에 이 차이를 명시해야 한다.** 명시하지 않으면 QUICK 구매자의 환불 요청 사유가 된다.

### 8-2. 추가 — 출력 분량 상한

`docs/pricing-unit-economics-and-input-limits.md`에 없던 항목을 §6으로 추가한다.

### 8-3. 추가 — 채우기 허용 조건

문항 구분 여부에 따른 기능 제한은 기존 어느 문서에도 없다. §5로 추가한다.

### 8-4. 무효화 — "BUILD는 채우지 않는다"는 현재 구현

문서에 적힌 결정이 아니라 구현에만 있던 정책이므로 문서 삭제 대상은 없다. 프롬프트와 코드 세 곳이 이 문서로 대체된다.

## 9. 명세와 구현의 격차 (이번 작업 범위 밖, 기록용)

`docs/create-mode-and-pricing-decision.md`가 정한 CREATE 명세와 현재 구현의 차이를 정직하게 남긴다.

| 명세 | 현재 |
|---|---|
| 부족한 사실만 1~3개씩 추가 질문 | 고정 10단계 폼. 사용자별 추가 질문 없음 |
| AI가 이해한 사실을 초안 전에 확인받음 | 확인 단계 없음 |
| 문항 개요 제안 후 사용자 승인 | 없음 |
| CREATE에서는 준비도 점수를 표시하지 않음 | 동일 파이프라인이라 점수가 표시됨 |

네 항목 모두 AI 호출이 늘어나므로 가격 재검토가 필요하다. 이번 작업에서는 다루지 않는다.

## 10. 구현 영향과 격리

변경은 BUILD 경로에만 닿아야 한다.

| 대상 | 성격 |
|---|---|
| `WRITING_MODE_INSTRUCTION.BUILD` | 모드별 맵의 한 항목. CREATE·POLISH에 물리적으로 영향 없음 |
| 목표 글자 수 지시문 | **공통 문장이므로 수정하지 않고 모드별로 분기**한다. 수정하면 POLISH가 함께 바뀐다 |
| `getAnalysisQuestions` | 빈 문항 필터. 5개 호출부가 모두 같은 함수를 부르므로 함께 움직인다 |
| `getUnansweredQuestions` | BUILD가 채우면 "제외했습니다" 안내와 모순되므로 함께 조정 |
| 검증기 | 빈 문항에 수치가 들어가면 `NEW_NUMBER`로 분석 전체가 실패한다. §3의 "수치 없이 완결" 규칙이 이 실패를 구조적으로 막는다 |
| 결과 화면 | 제안 표시와 복사 분리. 추가만 하며 기존 동작을 바꾸지 않는다 |

CREATE와 POLISH의 지시문이 바뀌지 않았음을 테스트로 고정한다. 사람이 눈으로 확인할 필요가 없어야 한다.

## 11. 롤백

이 결정 전체는 단일 커밋으로 되돌린다. 저장된 결과, 데이터베이스, 가격, 결제 흐름은 변경하지 않으므로 되돌려도 기존 사용자 데이터에 영향이 없다.
