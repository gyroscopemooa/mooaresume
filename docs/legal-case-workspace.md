# 법률 — 내 사건 워크스페이스

> 기준일: 2026-09-07 · 상태: **미리보기**(목록에 안 나오고 색인도 막힘). **출시 불가 — 5절의 대용량 문제가 먼저입니다.**
> 같이 볼 것: [`document-builders.md`](./document-builders.md)

## 1. 문서 열 개가 아니라 사건 하나

취업 쪽이 한 사람의 취업자료를 쌓는 구조라면, 법률은 **한 사건의 자료를 쌓는** 구조입니다. 소장을 쓸 때 넣은 계약서와 카톡은 석 달 뒤 준비서면에도, 다시 항소이유서에도 그대로 필요합니다. 문서마다 자료를 새로 올리게 만들면 세 번째쯤에서 사람이 떠납니다.

```
내 사건 (의료손해배상)
├ 자료   계약서·문자·녹취·판결문·상대 서면
├ 사건 분석 · 주요쟁점
├ 내용증명
├ 소장 / 답변서
├ 준비서면 1차, 2차
└ 판결문 분석 → 항소이유서
```

**연속성은 강제가 아닙니다.** 항소장 하나만 필요한 사람은 사건을 하나 만들고(무료·이름 한 칸) 판결문만 올린 뒤 그 문서만 결제하면 됩니다. 순서도, 나머지 문서 구매도 강제하지 않습니다.

## 2. 문서 10종과 단계

화면은 문서 이름이 아니라 **사람이 서 있는 자리**로 묶습니다. 소장을 받은 사람은 "답변서"라는 낱말은 몰라도 자기가 1심에 있다는 것은 압니다.

| 단계 | 문서 |
|---|---|
| 사건부터 이해하기 | 사건 분석 · 주요쟁점 정리 |
| 소송 전 | 내용증명 |
| 1심 | 소장 · 답변서 · 준비서면 · 증거 정리 · 상대방 서면 반박 |
| 판결 후 | 판결문 분석 · 항소장 · 항소이유서 |

내 지위(원고/피고/소송 전)에 따라 순서가 바뀝니다 — 소장을 받았으면 답변서가 앞으로 옵니다.

정의는 전부 `src/domain/legal-case.ts`의 `legalDocumentDefinitions` 한 곳에 있습니다. 종류마다 게이트웨이를 두지 않고 **설정표 하나 + 출력 스키마 하나**를 같이 씁니다. 문서를 더할 때 고칠 곳이 한 군데입니다.

## 3. 안전 규칙 — 취업 쪽과 다른 점

취업 문서에서 지어낸 문장은 면접에서 걸리지만, 여기서 지어낸 날짜는 소송을 끝냅니다.

- **기한을 계산하지 않습니다.** 항소기간을 모델의 산수에 맡길 수 없습니다. 기준만 적고("판결문을 송달받은 날부터") 날짜는 본인이 확인하게 합니다.
- **승소 가능성·확률을 말하지 않습니다.**
- **조문·판례를 기억으로 지어내지 않습니다.** 자료에 있는 것만 인용합니다.
- 고지 문구(`LEGAL_DISCLAIMER`)는 모델이 아니라 **코드가** 결과에 붙입니다. 모델에 맡기면 어떤 문서에는 빠집니다.
- 결제 전에 읽는 주의사항(`LEGAL_CAUTIONS`) 5개를 사건 시작 화면과 소개 글에 함께 싣습니다: 승소 장담 없음 / 자문 아님 / **모든 책임은 이용자 본인** / 기한 직접 확인 / 자료에 없는 것은 못 만듦.

**자료를 저장합니다.** 취업 쪽과 정반대입니다 — 사건은 저장이 곧 기능입니다. 대신 표마다 `owner_user_id`를 두고 RLS로 본인만, 사건을 지우면 자료·문서·결제기록이 함께 지워지고(cascade), 사건 화면은 `noindex`이며 서버 로그에 사건 내용을 남기지 않습니다.

## 4. 값과 한도

**서면 작성은 정액, 사건자료 분석은 분량제입니다.** 서면은 이미 정리된 사건 위에서 한 장을 쓰는 일이라 품이 비슷하고, 분석은 자료를 전부 읽는 일이라 분량이 곧 원가입니다.

| | 사건자료 분석 | 서면 작성 |
|---|---|---|
| ~300쪽 (기본) | 99,000원 | 99,000원 |
| ~700쪽 (대용량) | 149,000원 | 99,000원 |
| ~1,500쪽 (초대용량) | 199,000원 | 99,000원 |
| 1,500쪽 초과 | 별도 문의 | — |

### 판정은 AND입니다

| 플랜 | 페이지 | 파일 수 | 압축 해제 후 |
|---|---:|---:|---:|
| 기본 | 300 | 100 | 1GB |
| 대용량 | 700 | 200 | 2GB |
| 초대용량 | 1,500 | 400 | 4GB |

셋을 **모두** 만족해야 그 플랜입니다. 파일 50개에 320쪽이면 초과이고, 파일 110개에 150쪽이어도 초과입니다. 쪽수가 값을 정하는 축이고, 파일 수·용량은 비정상 업로드를 막는 울타리라 화면에서 크게 말하지 않습니다.

**ZIP은 압축 크기로 판정하지 않습니다.** 18MB짜리 ZIP이 풀리면 PDF 83개, JPG 420장, 2,800쪽일 수 있습니다. 그래서 순서가 곧 안전장치입니다.

```
업로드 → 압축 해제 → 파일·쪽수 계산 → 플랜 확정 → 그때 비로소 OCR/모델 호출
```

견적을 확정하기 전에는 돈이 나가는 일을 하나도 하지 않습니다. 압축파일 자체는 200MB까지, ZIP 안의 ZIP은 한 단계까지만 풉니다.

**값은 서버가 정합니다.** 결제 요청이 오면 서버가 저장된 자료를 다시 재서 플랜을 고릅니다 — 화면이 보낸 쪽수나 금액은 쓰지 않습니다. 1,400쪽 사건을 300쪽이라고 보내 기본가로 사는 길이 없습니다.

### 다섯 겹

1. 페이지 상한 (플랜)
2. 파일 수 상한
3. 압축 해제 후 용량 상한
4. 한 요청에 보내는 토큰 상한
5. **주문당 API 원가 차단기 8,000원** (`ORDER_API_BUDGET_KRW`)

다섯 번째가 마지막 문입니다. 앞의 넷을 다 지켜도 버그 하나면 원가가 터집니다 — 모델이 반복 호출되거나 재시도가 꼬리를 물 때, 페이지 수에는 막아 줄 것이 없습니다. 호출 **전에** 예상 원가를 재고 예산을 넘길 것 같으면 그 호출을 하지 않습니다. 7,000원을 넘으면 비싼 경로부터 닫습니다 — 결과가 조금 거친 것과 결과가 아예 없는 것은 손님에게 다른 일입니다.

## 5. 지금 못 하는 것 — 출시 전 필수

**상한이 6만 자(약 40쪽)입니다.** 1,400쪽을 넣으면 앞 3%만 읽습니다. 99,000원을 받고 40쪽만 읽은 문서를 주는 것은 기능의 한계가 아니라 사고라, 지금은 세 곳에서 그 사실을 말합니다(결제 단추 위 / 결과와 함께 / 업로드 시). 하지만 **말하는 것과 읽는 것은 다릅니다.**

필요한 것:

```
업로드 → 압축 해제 → 페이지 분해 → 읽기(4절 엔진) → 페이지별 저장(쪽번호 보존)
     → 타임라인·쟁점·증거 색인 → 필요한 20~100쪽만 상위 모델이 재검토 → 결과
```

**쪽번호를 절대 버리면 안 됩니다.** 결과에서 원문으로 되돌아갈 수 있어야 합니다.

```
쟁점 3. 수술 후 상태에 대한 설명의무
근거  진료기록 p.317 / 수술동의서 p.429 / 피고 준비서면 p.1,126
```

법률에서는 요약 정확도보다 이것이 중요합니다. 지금 `evidence` 필드가 그 방향인데 파일명까지만이고 쪽수가 없습니다.

## 6. 읽기 엔진 — Upstage(눈) + OpenAI(두뇌)

`src/domain/document-reading.ts`가 정책이고, 규칙은 셋입니다.

1. **한 쪽은 한 엔진만 읽습니다.** 같은 쪽을 Upstage와 OpenAI Vision에 둘 다 보내면 값이 두 배가 되는데 결과는 두 배로 좋아지지 않습니다.
2. **공짜부터.** 텍스트가 들어 있는 PDF·DOCX는 서버가 그냥 꺼냅니다.
3. **비싼 길은 필요할 때만.**

| 자료 | 엔진 |
|---|---|
| 글자가 있는 PDF·DOCX | 자체 추출 (0원) |
| 스캔 문서 | Upstage Document OCR |
| 표·양식이 복잡한 쪽 | 처음부터 Parse Standard (OCR 후 재시도하면 두 번 냄) |
| OCR이 흐리게 읽힌 쪽 | Parse Standard로 한 단계 승격 |
| 표·손글씨가 심한 쪽 | Parse Enhanced — **기본 닫힘**, 예산 넉넉할 때만 |
| 사진 자체가 증거 | OpenAI Vision (OCR은 "무엇이 찍혔는지"를 못 말합니다) |

승격은 **품질이 나쁘고 예산이 받쳐 줄 때만** 합니다. 승격하면 그 쪽은 값을 두 번 치르므로, 예산이 빠듯하면(`DEGRADE`) 거친 결과를 그대로 씁니다.

### 언제 Upstage를 버리는가

지금 쓰는 이유는 둘뿐입니다 — 한글 스캔·기울어진 사진·표에서 범용 모델보다 낫고, 페이지당 고정가라 원가를 미리 셀 수 있습니다. **둘 중 하나라도 무너지면 갈아탑니다.**

`READING_PROVIDER=OPENAI` 한 줄이면 끝입니다. 키가 없으면 설정과 무관하게 자동으로 OpenAI 경로로 내려갑니다 — 키를 아직 안 넣었다고 서비스가 멈추면 그건 안전장치가 아니라 고장입니다.

점검할 때 볼 것: OpenAI 쪽 읽기 품질이 Upstage를 따라잡았는가 / Upstage 품질이 떨어졌는가 / 값 차이가 사라졌는가. 하나라도 예면 OpenAI 단일 벤더가 낫습니다(키 하나, 장애 대응 한 곳, 개인정보 처리업체 하나).

단가는 `.env.example`의 `READING_PRICE_*`에 직접 넣습니다. 코드에 박지 않는 이유는 이 저장소가 이미 정한 규칙입니다 — **틀린 단가는 없는 것보다 나쁩니다.** 화면에 숫자가 떠 있으면 맞는 줄 알고 그 위에서 판단하게 됩니다.

## 7. 제품 표현

"법률상담", "변호사 검토"처럼 오인될 표현을 쓰지 않습니다. 쓰는 말: **사건자료 분석 · 법률문서 작성 지원 · AI 문서 검토 · 나홀로 소송 어시스턴트.**

## 8. 남은 일

1. **대용량 파이프라인**(5절) — 출시 전 필수
2. Upstage 키 연결 + `READING_PRICE_*` 채우기
3. 이미지 입력 받기 (지금은 PDF·DOCX·TXT·ZIP만)
4. 관리자 화면에 주문별 원가 기록 — 총 페이지 / 텍스트·Vision 페이지 / 모델별 비용 / 총 AI 원가. 50~100건 쌓인 뒤에 300쪽 상한과 벤더 선택을 다시 봅니다.
