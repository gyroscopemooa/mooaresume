# MOOA Resume 가격 원가 및 입력 한도 운영안

> 작성일: 2026-08-16

> 관련 문서: `MOOA_RESUME_PRODUCT_MODE_PRICING_ADDENDUM.md`, `MOOA_RESUME_PRICING_FLOW_MATRIX_ADDENDUM.md`, `MOOA_RESUME_LANDING_PRICING_FULL_TABLE_ADDENDUM.md`

## 1. 결론

현재 가격은 유지한다.

| 상품 | 가격 | 판매 단위 |
|---|---:|---|
| QUICK | 4,900원 | 작성된 지원서의 빠른 첨삭, 1개 지원 건 |
| PRO | 9,900원 | 공고와 지원자료를 포함한 1개 `ApplicationCase` |
| FINAL | 14,900원 | PRO 전체 기능과 제한된 AI 모의면접 세션 |

이 가격은 API 원가만으로는 충분히 성립 가능하다. 실제 위험 요인은 AI 토큰 단가보다 다음 항목이다.

- Polar의 저가 거래 건당 고정 수수료
- 한 결제로 여러 회사의 지원서를 처리하는 범위 악용
- 무제한 수정, 재생성, 자유 대화
- 환불, 고객지원, 광고비
- 모델 및 프롬프트를 구분하지 않은 과도한 고급 모델 호출

사용자에게 판매하는 단위는 글자 수나 메시지 수가 아니라 다음과 같다.

> 한 회사 · 한 직무 · 한 채용 시점의 `ApplicationCase` 1건

글자 수와 토큰 수는 상품 자체가 아니라 한 건의 합리적인 사용 범위를 지키는 기술적 제한으로 사용한다.

## 2. 수익 계산의 의미

여기서 계산하는 금액은 회계상 순이익이 아니라 **건당 공헌이익의 추정치**다.

건당 추정식:

```text
표시 판매가
- 표시가에 포함된 간접세
- Polar 결제 수수료
- Polar 출금 및 환전비의 건당 배분액
- OpenAI 사용료
- 파일 파싱·스토리지·서버 비용
- 재시도·환불·지원 충당액
= 건당 공헌이익
```

종합소득세 또는 법인세는 연간 소득, 사업자 형태, 비용 처리에 따라 달라지므로 판매 1건마다 고정 금액으로 계산하지 않는다. 출시 전 한국 세무 전문가에게 Polar Merchant of Record 정산 및 증빙 처리 방식을 확인한다.

## 3. 보수적인 현재 추정

다음은 의사결정을 위한 계획 가정이며 실제 정산표가 아니다.

- 한국 소비자 대상 세금 포함 표시 가격
- Polar 신규 Starter 수수료를 보수적으로 적용
- 국제 카드 가산 가능성 반영
- 환율은 계획 환율로 계산하고 실제 정산 시 갱신
- Polar 출금은 여러 주문을 묶어 월 단위로 수행
- 한국 사업자의 소득세·법인세, 광고비, 인건비 제외

| 상품 | VAT·Polar·출금 후 추정 | AI·기초 인프라 예상 | 운영비 전 공헌이익 예상 |
|---|---:|---:|---:|
| QUICK 4,900원 | 약 3,400원 | 약 400~700원 | 약 2,700~3,000원 |
| PRO 9,900원 | 약 7,500원 | 약 900~1,500원 | 약 6,000~6,600원 |
| FINAL 14,900원 | 약 11,700원 | 약 1,500~2,500원 | 약 9,200~10,200원 |

위 범위는 모델 라우팅과 호출 제한이 정상적으로 동작한다는 전제다. 환불, 사람의 고객지원, 무료 재분석, 광고비가 포함되면 실제 이익은 낮아진다. 특히 QUICK은 신규 고객 획득용 진입 상품으로 보고 단독 상품 이익률만 최적화하지 않는다.

## 4. 공식 요금 정보 처리 원칙

OpenAI와 Polar 요금은 바뀔 수 있으므로 Markdown에 적힌 숫자를 결제 또는 원가 계산의 영구 상수로 사용하지 않는다.

- 출시 직전 공식 OpenAI 가격표를 다시 확인한다.
- 실제 사용 모델의 입력·출력·캐시·도구 호출 단가를 별도 설정값으로 관리한다.
- Polar 조직 생성 시점에 적용되는 플랜과 국제 카드 가산 수수료를 실제 대시보드에서 확인한다.
- 한국 고객의 세금 포함 표시와 Polar balance 정산 내역을 테스트 주문으로 검증한다.
- 환율은 비용 대시보드에서 갱신 가능한 값으로 둔다.

참고 대화의 모델 가격과 이전 조사 시점의 공식 가격 사이에 차이가 있으므로, 특정 모델 단가는 출시 시점 확인 전까지 확정값으로 간주하지 않는다.

## 5. 모델 라우팅 원칙

모든 단계를 최고가 모델로 실행하지 않는다.

| 작업 | 권장 모델 등급 |
|---|---|
| 파일 텍스트 정리, 필드 추출, 중복 탐지 | 저비용 모델 |
| 문항 의도, 공고·경험 매칭, 핵심 평가 | 중간 등급 모델 |
| 최종 문장 작성, 어려운 판단, 독립 재평가 | 필요할 때만 상위 모델 |
| 글자 수, 문항 수, 중복 해시, entitlement | 결정론적 코드 |

검색은 기본 호출에 포함하지 않는다. 사용자가 제공한 공고와 자료를 우선 사용하고, 최신 기업 정보 확인 등 실제로 검색이 필요한 작업에만 제한적으로 사용한다.

## 6. 입력 한도 정책

### QUICK

- 한 회사·한 직무·한 지원 건
- 권장 자소서 본문: 총 7,000자
- 7,000자는 결제를 즉시 요구하는 hard limit가 아니라 soft limit
- 같은 지원 건의 문항이 조금 긴 경우 계속 입력 허용
- 초기 내부 hard cap 후보: 총 10,000~12,000자
- 다른 회사나 다른 직무의 지원서는 새 `ApplicationCase`로 분리

7,000자를 넘었을 때의 권장 문구:

```text
지원서가 조금 깁니다.
같은 지원 건의 추가 문항이라면 계속 추가할 수 있어요.
```

### PRO

PRO에 QUICK과 동일한 7,000자 제한을 적용하지 않는다.

포함 범위:

- 채용공고 1건
- 자소서 여러 문항
- 이력서·경력기술서·포트폴리오 등 합리적인 수의 지원자료
- 추가 경험 정보
- 정상적인 범위의 질문, 작성, 수정, 최종 검수

사용자 화면에는 지나치게 세세한 토큰 제한을 노출하지 않고, 서버에서 다음 제한을 둔다.

- 문서별 크기 및 전체 파싱 길이
- 문항 개수
- 생성·수정 라운드
- 대화 컨텍스트 길이
- 동일 요청 반복
- Case 활성 기간

### FINAL

FINAL은 무제한 자유 채팅이 아니다.

- PRO와 동일한 지원 건을 기반으로 한다.
- 1개 모의면접 세션을 기본 단위로 한다.
- 기본 질문, 동적 꼬리질문, 답변 평가, 취약 질문 재훈련의 합리적인 상한을 서버에서 관리한다.
- 영상·화상 면접은 현재 상품 범위가 아니다.

## 7. 입력 UI의 플러스 버튼

플러스 버튼은 `7,000자 추가 구매`가 아니라 **같은 지원서의 문항 또는 자료 추가**로 정의한다.

```text
[+ 문항 추가]
[+ 지원자료 추가]
```

버튼을 눌렀을 때 사용자가 다른 회사의 지원서를 계속 추가할 수 있는 무제한 텍스트 슬롯을 제공하지 않는다. 각 문항과 문서는 현재 `ApplicationCase`에 연결한다.

결제 전에는 사용자가 필요한 문항을 모두 추가할 수 있게 하고, 서버가 전체 범위를 확인한 뒤 한 번의 결제 금액을 결정하는 방식이 가장 자연스럽다.

## 8. 추가 분량 결제 정책

MVP에서는 `+7,000자 1,000원`과 `+7,000자 5,000원`을 모두 도입하지 않는다.

### 1,000원이 부적합한 이유

- Polar의 건당 고정 수수료 비중이 지나치게 크다.
- 결제 완료 후 추가 결제라면 비용 대비 남는 금액이 매우 작다.
- 잦은 소액 체크아웃은 UX와 환불 처리를 복잡하게 만든다.

### 5,000원이 부적합한 이유

- QUICK 한 건 가격과 거의 같다.
- 사용자는 단순 글자 추가가 아니라 새 상품을 다시 사는 느낌을 받는다.
- 같은 지원 건의 문항이 조금 많다는 이유로 과도한 가격 상승이 발생한다.

추가 요금이 실제로 필요해지면 다음 후보를 검토한다.

1. 결제 전 분량을 계산해 동일 체크아웃에 1,900~2,900원을 합산
2. QUICK Plus 7,900원 상품으로 최대 약 14,000자 또는 더 많은 문항 제공
3. 결제 후에는 같은 Case 전용 2,900~3,000원 확장권 제공
4. QUICK에서 PRO로 5,000원 차액 업그레이드

추가 분량 상품은 반드시 같은 회사·같은 직무·같은 채용 시점에만 사용할 수 있게 entitlement를 검사한다.

## 9. Polar 구현 방향

Polar를 단일 고정 상품만 가능한 시스템으로 가정하지 않는다. 고정 가격, 사용량 기반 가격, 선불 크레딧 또는 계산된 체크아웃 가격을 기술 검토할 수 있다.

다만 가능한 기능과 MVP에 적합한 UX는 별개다.

- 결제 전 옵션은 가능한 한 한 번의 체크아웃으로 합산한다.
- 이미 결제한 뒤의 추가 구매는 새 결제가 발생할 수 있음을 전제로 한다.
- 1,000원 수준의 독립 top-up 상품은 만들지 않는다.
- 크레딧이 소진되었을 때의 접근 차단은 애플리케이션 entitlement에서 직접 수행한다.
- webhook으로 결제가 확인된 뒤에만 Case 권한과 크레딧을 부여한다.
- Polar의 ad-hoc price 및 결합 결제 지원 범위는 구현 시점 공식 문서와 테스트 환경에서 다시 검증한다.

## 11. 가격 재검토 시점

초기 100건 또는 각 상품별 최소 30건의 유효 결제가 쌓이면 다음을 검토한다.

- 상품별 평균 및 P50/P95 입력 토큰
- 상품별 평균 및 P50/P95 출력 토큰
- 평균 모델 호출 수와 재시도율
- 평균 수정 라운드
- 분석 실패 및 무료 재실행 비율
- 환불률과 고객지원 시간
- Case당 파일 파싱·스토리지 비용
- 광고비를 포함한 고객 획득비용
- QUICK에서 PRO 및 FINAL로의 전환율
- 7,000자를 넘는 정상 사용자의 비율
- 서로 다른 회사 지원서를 한 Case에 넣는 악용 비율

가격이나 한도를 바꿀 때는 평균값만 보지 않고 P95 비용과 정상 사용자의 이탈률을 함께 본다.

## 13. 외부 노출 원칙

가격표에는 사용자가 이해해야 할 범위만 표시한다.

```text
QUICK
작성한 지원서 빠른 첨삭
한 회사·한 직무의 지원서 1건

PRO
공고와 지원자료를 함께 보는 정밀 분석
한 지원 건 전체

FINAL
PRO 전체 기능과 실제 지원자료 기반 AI 모의면접
```

내부 토큰 수, 모델 라우팅, 재시도 상한, hard cap, 비용 임계값은 외부 기능표에 공개하지 않는다.
