# 자소서 밖으로 — 문서 종류를 하나 더 늘리기 위한 구도

작성: 2026-09-06 · 상태: **설계안(코드 변경 없음)** · 결정이 필요한 항목은 맨 끝에 모았습니다.

목표: 지금 자기소개서 하나에만 맞춰진 제품을, 이력서·경력기술서·포트폴리오·
대학원 서류·법률 서면까지 같은 엔진으로 처리하는 제품으로 넓히는 것.
런칭 준비이므로 "무엇을 언제 열 것인가"까지 같이 적습니다.

## 1. 지금 어디가 자소서에 묶여 있나 (조사 결과)

| 층 | 파일 | 자소서 전제 | 얼마나 깊나 |
|---|---|---|---|
| 요청 계약 | `src/application/analysis-contract.ts` | `documents.kind` 8종이 전부 채용 맥락, `questions[]`(문항) 필수 | **얕음** — 축 하나 더하면 됨 |
| 프롬프트 | `src/server/ai/quick/prompt.ts:127` | `"당신은 한국어 자기소개서 첨삭 엔진입니다."` + 문항·면접관·채용공고 규칙 | **깊음** — 3층으로 나눠야 함 |
| 결과 스키마 | `src/domain/result-document.ts` (393줄) | `questions[]`, `revisions[].questionOrder`, `interviewRisks`, `requirementMatch`(공고 대조) | **중간** — 코어와 자소서 전용을 갈라야 함 |
| 입력 화면 | `pro-input-page.tsx`(486줄), `simple-intake.tsx`(506줄) | 문항 카드, 목표 글자 수, 공고 업로드 | **중간** — 껍데기는 재사용 가능 |
| 문서 분류 | `src/domain/document-classify.ts` | 8종 라벨·파일명 규칙 | **얕음** — 목록 확장 |
| DB | `public.document_kind` enum | 위와 같음 | 얕음(enum 추가 마이그레이션) |

**핵심 발견 하나.** 이 제품의 진짜 코어는 "자소서를 잘 쓴다"가 아니라
**근거 검증**입니다 — `evidenceQuote`는 지원자가 낸 문서에 실제로 있는 문구여야
하고, 없는 사실은 만들지 말고 질문으로 남긴다(`prompt.ts:135,142-144`).
이 규칙은 **문서 종류와 무관하게 그대로 값을 합니다.** 오히려 법률 서면이나
연구계획서에서 더 중요합니다. 그래서 확장은 "새 제품 만들기"가 아니라
**같은 검증 엔진에 입출력 껍데기를 갈아 끼우기**입니다.

## 2. 축 하나를 더한다

지금 요청은 두 축입니다.

```
product     : QUICK | PRO | FINAL          (얼마나 깊이)
writingMode : CREATE | BUILD | POLISH      (없는 걸 쓰나 / 채우나 / 다듬나)
```

여기에 세 번째 축을 더합니다.

```
docType     : COVER_LETTER | RESUME | CAREER_DESCRIPTION | PORTFOLIO_NOTE
              | STUDY_PLAN | LEGAL_BRIEF | ...
```

세 축은 **곱하지 않습니다.** 문서 종류마다 의미 있는 조합만 엽니다(4절 표).
예: 이력서에 `CREATE`(맨바닥에서 창작)는 열지 않습니다 — 이력서는 사실의
목록이라 없는 경력을 지어내면 그건 위조입니다.

### "문항"을 "구획"으로 일반화

자소서의 문항 1·2·3은 다른 문서에서는 이렇게 대응됩니다.

| 문서 | 구획(section)이 되는 것 |
|---|---|
| 자기소개서 | 문항 (지금 그대로) |
| 이력서 | 경력 항목 하나하나 |
| 경력기술서 | 프로젝트/업무 단위 |
| 포트폴리오 설명글 | 작업물 한 건 |
| 연구계획서 | 연구 배경 / 목적 / 방법 / 일정 |
| 준비서면 | 쟁점 하나 |

**필드 이름은 바꾸지 않습니다.** `questions[]`·`questionOrder`를 그대로 두고
docType별 어댑터가 "구획"을 그 모양으로 채웁니다. 이름을 바꾸면 결과 문서
스키마·저장된 과거 결과·화면까지 전부 따라 움직여야 하는데, 얻는 것은
용어의 정확함뿐입니다. 화면에 보이는 **라벨만** docType별로 다르게 합니다.

### 프롬프트 3층

```
1층 (공통·불변)  사실 날조 금지 · 인용은 제출 문서에서만 · 길이 무결성
                 → 지금 prompt.ts에 이미 있는 규칙 대부분이 여기로
2층 (docType)    누구로서 읽는가 + 무엇을 보는가
                 이력서: 채용담당자가 6초 안에 훑는다 / 성과는 수치와 역할
                 준비서면: 재판부가 쟁점 단위로 읽는다 / 주장-근거-법적평가
3층 (mode)       CREATE / BUILD / POLISH (지금 그대로)
```

## 3. 화면 구도 (요청하신 왼쪽 드로어)

지금 홈에는 좌측 드로어가 **하나** 있습니다 — `CareerAssessmentDrawer`
(접히면 나침반 마크 + "커리어/검사" 세로 라벨). 같은 자리에 **두 번째 마크**를
답니다.

```
접힘 상태 (화면 왼쪽 가장자리, 세로로 두 개)
  ┌──┐
  │🧭│  커리어 검사   ← 기존 (건드리지 않음)
  ├──┤
  │📄│  서류 종류     ← 신규
  └──┘

열림 상태 — 간단한 목록 하나
  서류 종류 고르기
  ─────────────────
  자기소개서            지금 쓰는 것
  이력서                경력을 한 장으로
  경력기술서            무엇을 했는지 자세히
  포트폴리오 설명        작업물에 붙이는 글
  ─────────────────
  대학원 · 연구계획서    학업계획서 · 연구계획서
  ─────────────────
  법률 서면             준비서면 · 항소이유서 · 쟁점요약   [준비 중]
```

고르면 → **지금 프로 빌드와 같은 심플 입력 화면**으로 들어갑니다.
문서 종류에 따라 입력 칸의 라벨과 개수만 달라집니다.

**구현 원칙:** `CareerAssessmentDrawer`를 고치지 말고 **형제 컴포넌트**로
새로 만듭니다(`document-type-drawer.tsx`). 두 드로어가 같은 가장자리를 쓰므로
세로 위치만 서로 비키게 하고, 하나가 열리면 다른 하나는 접습니다.
CSS는 기존 드로어의 것을 복사해 시작합니다 — 공유하면 커리어 쪽 조정이
서류 쪽을 깨뜨립니다.

### 라우트

기존 `/final/build`·`/create`·`/polish`는 **자소서 전용으로 그대로 둡니다**
(색인된 주소이고 지금 매출이 나오는 경로입니다). 새 종류는 형제 계열로:

```
/write/[docType]/[mode]      예: /write/resume/build
```

`docType=cover-letter`는 기존 화면으로 되돌려 보내(redirect) 두 벌을 만들지
않습니다.

## 4. 문서별 명세와 난이도

| # | 문서 | 여는 모드 | 필요한 입력 | 출력의 핵심 | 난이도 | 위험 |
|---|---|---|---|---|---|---|
| 1 | **이력서** | BUILD · POLISH | 기존 이력서 + 공고(선택) | 항목별 재작성, 공고 대조, 빠진 것 | 낮음 | 낮음 |
| 2 | **경력기술서** | BUILD · POLISH | 경력기술서 + 이력서 | 프로젝트 단위 STAR 정리, 수치화 | 낮음 | 낮음 |
| 3 | **포트폴리오 설명글** | BUILD · POLISH | 작업물 설명 + 이미지 설명 | 작업 한 건당 문제-과정-결과 | 낮음 | 낮음 |
| 4 | **학업·연구계획서** | BUILD · POLISH | 초안 + 학과/전공 정보 + 경력 | 연구 질문의 구체성, 지도교수 적합성, 실현 가능성 | 중간 | 중간 — 선행연구 인용을 모델이 지어낼 수 있음 |
| 5 | **법률 서면** | POLISH만 (1차) | 초안 + 사건 개요 | 쟁점 정리, 주장-근거 연결, 가독성 | 중간 | **높음** (6절) |

**1·2·3은 이미 절반 이상 되어 있습니다.** 이력서·경력기술서·포트폴리오는
이미 `documents.kind`에 있고, 프롬프트가 근거 자료로 읽고 있습니다.
바꾸는 것은 "참고 자료"에서 "첨삭 대상"으로 자리를 옮기는 일입니다.

## 5. 런칭 순서

**1차 (지금 준비 · 2~3주 규모)** — 이력서 · 경력기술서
- 이유: 입력이 이미 있고, 결과 스키마도 거의 그대로 쓰이며, 자소서 손님이
  그대로 넘어옵니다("이력서도 봐주나요"는 지금도 들어오는 질문입니다).
- 이것으로 `docType` 축과 드로어를 실제로 검증합니다.

**2차** — 포트폴리오 설명글 · 학업/연구계획서
- 연구계획서는 **선행연구·논문 인용을 모델이 만들지 못하게** 막는 규칙이
  1차에서 검증된 뒤에 엽니다.

**3차** — 법률 서면 (범위를 좁혀서, 6절 조건 아래)

각 차수는 **베타 게이트**를 답니다: 종류별로 `enabled` 플래그를 환경변수로
두고, 드로어 목록에는 "준비 중"으로 보여 주되 눌리지 않게 합니다. 커뮤니티
자동글의 `COMMUNITY_SEED_ENABLED`와 같은 방식입니다 — 이상하면 배포 없이 끕니다.

## 6. 법률 서면 — 하는 것과 절대 안 하는 것

수요가 있다는 판단에는 동의합니다(나홀로소송·내용증명은 실제로 검색량이
큽니다). 다만 **"문장이 그럴듯하게 나온다"와 "써도 되는 서면이다"는 다릅니다.**
정직하게 적습니다:

- 이 영역에서 AI가 가장 잘 저지르는 실수는 문장이 아니라 **법조문·판례 번호를
  지어내는 것**입니다. 없는 판례를 인용한 서면을 낸 사례가 해외에서 이미 여러
  건 제재로 이어졌습니다.
- 서면은 **기한**이 걸려 있습니다(항소기간 등). 기한을 잘못 안내하면 그 사람은
  권리를 잃습니다. 이건 첨삭 실수가 아니라 회복 불가능한 피해입니다.
- 사실관계를 모델이 매끄럽게 "보완"하면 그것은 **허위 주장**이 됩니다.
  자소서에서는 과장이지만 서면에서는 성격이 다릅니다.

그래서 범위를 이렇게 좁히면 **안전하게 열 수 있습니다**:

| 한다 | 하지 않는다 |
|---|---|
| 이미 쓴 초안의 **구조**를 쟁점 단위로 정리 | 법률 자문 · 승소 가능성 판단 |
| 주장과 근거가 **연결되어 있는지** 표시 | 법조문·판례를 **새로 인용** (한 건도) |
| 문장 가독성·중복·감정적 표현 다듬기 | **기한·절차 안내** (항소기간, 관할 등) |
| 빠진 것을 **질문으로** 남기기 | 사실관계 보충·추정 |
| 서식 체계(제목·항목 번호) 점검 | 서면을 **처음부터 작성**(CREATE 모드 미개방) |

추가로 필요한 것:
1. 화면 상단 고정 문구 — "법률 자문이 아닙니다. 제출 전 변호사 검토를 권합니다."
2. 프롬프트 1층에 **인용 금지 규칙**을 하드 추가 + 출력 검증기에서
   `제○조`·`○○다○○○○` 형태의 문자열이 **초안에 없던 것**이면 차단.
   (지금 근거 검증기가 하는 일과 같은 방식이라 재사용 가능합니다.)
3. 1차 대상은 **준비서면·쟁점요약서**로 시작. 항소이유서는 기한이 직접 걸려
   있어 마지막에 둡니다.

> 참고로 **내용증명·진정서**는 법적 위험이 서면보다 훨씬 낮으면서 수요는
> 비슷합니다. 법률 갈래의 첫 상품으로는 이쪽이 낫습니다.

## 8. 결정이 필요한 것 (사용자)

1. **가격** — 새 종류를 기존 QUICK/PRO/FINAL 안에 넣을지, 종류별로 따로 매길지.
   (권고: 1차는 기존 등급 그대로. 축이 하나 더 늘면 가격표가 3×3이 됩니다.)
2. **드로어 라벨** — "서류 종류" / "무엇을 첨삭할까요" / "문서 선택" 중 어느 것.
3. **법률 갈래 첫 상품** — 준비서면부터인지, 내용증명부터인지.
4. **1차 범위** — 이력서·경력기술서 둘 다인지, 이력서 하나로 좁힐지.
5. **영문 서류** — SOP·영문 이력서를 1차에 포함할지(트랜스트림과 달리 여기는
   한국어 전제가 프롬프트 전반에 깔려 있어 별도 작업입니다).
