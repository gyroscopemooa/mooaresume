# "챗GPT에 파일 3개 올린 거랑 뭐가 다른가" — 지적과 코드 대조

- 출처: 사용자 대화, 2026-08-31. 지적은 사용자가 ChatGPT와 나눈 분석이고, 대조와 판단은 Claude가 코드를 읽고 붙였습니다.
- 상태: **기록 문서.** 이 문서로 바뀐 코드는 없습니다.
- 같이 볼 것: [`positioning-and-differentiation.md`](./positioning-and-differentiation.md)(2026-08-29 포지셔닝 메모), [`analysis-consistency-and-rounded-editing-philosophy.md`](./analysis-consistency-and-rounded-editing-philosophy.md)(첨삭 철학).

---

## 1. 지적의 요지

> 공고 + 이력서 + 자소서를 넣고 AI가 읽고 첨삭한다면, 챗GPT에 파일 3개 올리고 "이 공고 기준으로 첨삭해줘"라고 하는 것과 본질적으로 같다.

그리고 제안된 방향:

1. **"GPT보다 좋은 AI"로 팔지 말 것.** "GPT로 30분 프롬프트 쳐야 할 일을 자료만 넣으면 3분에 끝내는 도구"로 팔 것.
2. 한 덩어리 답변 대신 **① 공고 구조화 → ② 내 자료 매칭 → ③ 문항별 검수 → ④ 누락 탐지 → ⑤ 수정 → ⑥ 제출 전 교차검증** 의 고정 공정으로 만들 것.
3. 킬러 기능은 **누락 탐지** — "내가 뭘 빠뜨렸는지" 찾아주는 것.
4. **사실 추출과 AI 해석을 분리**할 것. "필수역량 6개"는 위험하고, "공고에 명시된 것 / 문맥상 추정되는 것"으로 나눠야 한다.
5. **"협업 능력이 없다"가 아니라 "제출 자료에서 확인되지 않는다"**로 말할 것. 이 차이가 크다.
6. **점수 남발을 뺄 것.** 근거 없는 정밀성이 신뢰를 깎는다. `충족 / 부분 충족 / 확인 필요 + 판단 근거`가 낫다.

## 2. 코드와 대조

지적은 코드를 보지 않은 상태에서 쓰였습니다. 실제로는 **제안된 구조의 대부분이 이미 스키마에 있습니다.**

| 제안 | 지금 있나 | 어디에 |
|---|---|---|
| 공고 요구사항 ↔ 내 자료 대조 | **있음** | `requirementMatchSchema` — `requirement / status / evidence / recommendation` |
| 충족·부분 충족·미확인 3단계 | **있음** | `status: "matched" \| "partial" \| "missing"` |
| 판단 근거를 원문으로 보여주기 | **있음** | `evidenceSchema` — `source(resume/job_posting/reference/user_answer) + quote` |
| 사실과 해석 분리 | **있음** | `issueSchema.category: "objective" \| "qualitative" \| "needs_verification"` |
| 서류 간 교차검증(회사명·기간·학력·공백) | **있음** | `documentConflictSchema` — `field` 9종, `resumeStatement` vs `coverLetterQuote` |
| 원문 → 문제 → 수정문 → 이유 | **있음** | `resultQuestionSchema` — `originalAnswer / originalAnnotations / revisedAnswer / revisionReasons` |
| 경험 중복 탐지 | **있음** | `resultPrioritySchema.category: "duplication"` |
| 추상표현 지적 | **있음** | `originalAnnotation.type: "vague"` |
| 글자 수 | **있음** | `category: "length"` |
| 소신/둥글게 선택 | **있음** | `writingStyle`, `editing-stance.ts` |
| 면접 리스크·예상 질문 | **있음(제안에 없던 것)** | `interviewRiskSchema`, `interviewQuestionSchema` |
| 이력 타임라인 | **있음(제안에 없던 것)** | `careerTimelineEntrySchema` |
| 오탈자 전용 검사 | **약함** | 별도 항목 없음. `polish` 주석에 섞임 |
| 공고를 "명시 / 추정"으로 나눠 보여주기 | **없음** | 요구사항은 평평한 목록 하나 |

**즉 지적의 ①~⑥ 공정 중 ②③④⑤⑥은 이미 만들어져 있고, ①만 반쯤 되어 있습니다.**

그리고 지적이 "위험하다"고 한 것도 이미 지켜지고 있는 쪽이 많습니다. `/examples` 화면의 준비도 점수에는 이미 **"합격확률이 아닌 제출 준비 상태"**라는 문구가 붙어 있습니다.

## 3. 판단

### 3-1. 진단은 맞고, 이미 우리 전략이다

`positioning-and-differentiation.md`에 두 줄로 이미 적혀 있습니다.

```
"ChatGPT에서도 할 수 있음"   → 상관없음
"ChatGPT에서 하는 게 더 편함" → 위험함
```

이 지적은 같은 결론에 다른 길로 도착한 것입니다. 새 전략이 아니라 **기존 전략의 재확인**으로 취급하는 게 맞습니다.

### 3-2. 진짜 문제는 기능이 아니라 "말하지 않는 것"이다

교차검증은 만들어져 있는데, **밖에서는 그 얘기를 안 합니다.** 랜딩·요금·FAQ 어디에도 "이력서와 자소서의 회사명·경력기간 불일치를 잡아준다"는 말이 없습니다.

기능을 더 만드는 것보다 **이미 만든 것을 제품 설명의 1번으로 올리는 것**이 지금 더 급합니다. 안 팔리는 이유가 없어서가 아니라 안 보여서일 때, 더 만드는 건 답이 아닙니다.

### 3-3. 점수 얘기는 반만 동의한다

**동의:** 하위 점수 `구체성 61 / 논리 74 / 설득력 68`은 빼거나 등급으로 바꾸는 게 맞습니다. 61과 68의 차이를 설명할 방법이 없습니다. 근거 없는 소수점이 바로 지적이 말한 "근거 없는 정밀성"입니다.

**반대:** 준비도 총점까지 없애는 건 과합니다. 이유 두 가지.

- 숫자는 **"다시 볼 이유"**를 만듭니다. 고치고 다시 돌렸을 때 72 → 81은 사용자가 유일하게 즉시 이해하는 진전입니다. 등급만 있으면 "보통 → 보통"이 되어 아무것도 안 바뀐 것처럼 보입니다.
- 이미 **"합격확률이 아닌 제출 준비 상태"**라는 방어 문구가 붙어 있습니다. 위험한 건 숫자 자체가 아니라 *합격률로 읽히는* 숫자입니다.

정리하면 **총점 1개는 남기고 하위 점수 5~7개를 없애는 것**이 이 지적의 정확한 실행입니다.

### 3-4. 제일 값어치 있는 건 ④ 누락 탐지가 맞다

여기는 동의합니다. 그리고 이건 **챗GPT가 구조적으로 잘 못하는 영역**입니다. 이유가 있습니다.

챗GPT에 자료를 다 올려도 사람은 "첨삭해줘"라고 씁니다. 그러면 모델은 **눈앞의 글을 고칩니다.** 없는 것을 찾으려면 "공고의 요구사항을 전부 나열하고, 그 각각에 대해 내 자료 전체에서 근거를 찾고, 근거가 없는 항목만 남겨줘"라고 시켜야 하는데, 그렇게 시키는 사람은 거의 없습니다.

**AI 성능 차이가 아니라 "무엇을 시킬지 아는가"의 차이이고, 그건 제품이 대신 가질 수 있습니다.** 계산기와 엑셀의 차이가 계산 능력이 아닌 것과 같습니다.

### 3-5. 표현 규칙은 하나만 지키면 된다

지적 중 실무적으로 가장 값진 한 줄:

> "협업 능력이 없다"가 아니라 **"제출 자료에서 확인되지 않는다"**

전자는 사람에 대한 판정이라 틀리면 모욕이 되고, 후자는 서류에 대한 관찰이라 틀려도 "아 그건 이력서에 안 썼네"로 끝납니다. **없는 것을 지적하는 기능을 미는 이상, 이 문장 규칙이 안전장치의 전부입니다.** `missing` 상태의 문구를 이 규칙으로 고정해 두면 나머지 위험은 대부분 사라집니다.

## 4. 그래서 남는 할 일

만들 것보다 **정리하고 드러낼 것**이 많습니다.

| | 할 일 | 크기 |
|---|---|---|
| 1 | `missing` 문구를 "확인되지 않습니다" 형태로 고정 | 작음 (프롬프트) |
| 2 | 하위 점수 5~7개 제거, 준비도 총점만 유지 | 중간 (스키마+화면) |
| 3 | 공고 요구사항을 **명시 / 추정** 두 묶음으로 분리 | 중간 (스키마+프롬프트) |
| 4 | 교차검증·누락 탐지를 랜딩과 요금 화면 1번으로 | 작음 (문구) |
| 5 | 오탈자 전용 항목 | 작음 |

**하지 말 것:** 지적에 나온 기능을 새로 만들기. 대부분 이미 있습니다. 같은 걸 두 번 만들면 두 개를 유지해야 합니다.

## 5. 한 줄 정리

> 무아레쥬메 PRO는 자소서를 대신 써주는 서비스가 아니라, **공고·이력서·자소서를 서로 대조해서 서류에서 빠진 부분을 찾아주는 AI 서류검수**다.

이 문장은 지적에서 그대로 가져왔고, **이미 코드가 하고 있는 일과도 맞습니다.** 바꿔야 할 것은 제품이 아니라 제품 설명입니다.
